# Per-Env Services Design

Date: 2026-08-05
Status: Approved (design review)

## Problem

`[stack].services` is a single list that drives both dev and prod
compose rendering. It is impossible to run a sidecar in dev but not in
prod (e.g. SeaweedFS in dev, AWS S3 in prod) or to use different DBs
(MySQL in dev, Postgres in prod). The prod compose file is generated
once at `pier init` and synced verbatim on every deploy, so even a
manual `[stack].services` edit never reaches the server unless the
compose file is regenerated by hand.

## Goals

1. Per-env service lists in pier.toml, expressed in the same
   `services = [...]` style as `[stack].services`.
2. `pier init` scaffolds the same services for dev and production.
3. A single `pier service [env]` command (init-style picker) manages
   both dev and per-env service lists — `add`/`remove` subcommands
   are removed.
4. `pier deploy <env>` re-renders `docker-compose.prod.yml` from
   pier.toml at deploy time (implementing the stubbed render phase),
   preserving user edits via a merge.
5. Services removed from an env are torn down on the remote (the
   running container is stopped and removed); volumes are preserved.

## 1. Config model

New optional field on `DeployConfig` (internal/config/config.go):

```toml
[deploy.production]
services = ["meilisearch", "postgres", "redis", "queue", "scheduler"]
```

- `Services []string toml:"services"` — optional **full list** for the
  env. When absent, the env inherits `[stack].services`.
- Effective list: `effective(env) = deploy.<env>.services` if present,
  else `[stack].services`. DevOnly filtering (mailpit) happens at
  render time exactly as it does for `[stack].services` today — mailpit
  may appear in a prod list and is silently excluded from the compose.
- New `Config.ServicesForEnv(env string) []string` helper in the
  config package implementing the above.
- `GenerateProdFiles` and `renderProdCompose` switch from
  `cfg.Stack.Services` to `cfg.ServicesForEnv(env)`.
- Existing unknown-name error path is reused: a typo like `se3` in
  `deploy.<env>.services` fails at render with
  `laravel: unknown service "se3"` (same as `[stack].services` today).
  Config.Validate does not check names — it cannot import the stack
  package (import cycle).

## 2. Validation relaxation (scaffold rule)

`Config.Validate` currently rejects every `[deploy.<env>]` table
missing `host`, `user`, `path`, or `branch`. The init scaffold
(below) writes a table containing only `services`, so the rule is
relaxed:

- All four of `host/user/path/branch` empty → **allowed** (unconfigured
  scaffold). `pier deploy <env>` already fails at preflight with
  `deploy.<env>.host is empty`.
- Any subset set (partially configured) → still an error, as today.

## 3. pier init scaffold

`runInit` writes the chosen services into both places in pier.toml:

- `[stack] services = [...]` (existing behavior).
- `[deploy.production] services = [...]` with the **same list** — the
  table is created only when the user picked at least one service.
  No host/user/path/branch are written; the user fills them in later.
- The prod files generated at init time
  (`GenerateProdFiles(cfg, "production")`) automatically reflect the
  scaffolded list, since init's `cfg.Deploy["production"].Services`
  is set.

## 4. CLI: `pier service [env]`

The `add` and `remove` subcommands are removed; the `service` command
is now `pier service [env]`, driven by the init-style multi-select
picker:

- **`pier service`** (no arg) — dev services. Picker shows all
  `SupportedServices()` with `[stack].services` pre-ticked. On
  confirm:
  - Write the new list to `[stack].services`.
  - Re-render `docker-compose.yml` via `rerenderDevCompose`
    (existing behavior).
  - `docker compose up` the newly added services unless `--no-up`
    (existing behavior). Removed dev containers are left running, as
    today.
  - Print `added: [...] removed: [...]`.
- **`pier service <env>`** — that env's services. The arg is always
  treated as an env name; bare service names are not accepted (a
  service named like an env is still edited through the picker).
  - Env must exist in `cfg.Deploy`; otherwise the same error as
    `pier deploy`: `no [deploy.<env>] section in pier.toml`.
  - Picker shows all `SupportedServices()` with the effective list
    (`cfg.ServicesForEnv(env)`) pre-ticked.
  - On confirm: if the result equals the current effective list
    (sorted), nothing is written (no-op — no needless
    materialization). Otherwise write the result to
    `deploy.<env>.services`, creating the map entry if missing.
    Empty result writes `services = []` (explicitly no sidecars in
    prod — distinct from inherit).
  - No local compose re-render; the next deploy re-renders prod
    files and tears down removed containers.
- **Non-TTY** (`tui.ShouldRun()` false) → error telling the user the
  command is interactive and to edit pier.toml instead. (Today's
  non-TTY `pier service add` with no names silently no-ops; with the
  names form gone, an explicit error is clearer.)
- Flags: `--no-up` stays. `--no-stop` is removed (dead code in the
  remove path).

TUI package: `PickServicesToAdd`/`PickServicesToRemove` are replaced
by a single `PickServices(available, current []string) ([]string,
error)` — a multi-select with `current` pre-ticked (presets map for
`NewMultiPicker`). Same `ErrAborted` / empty-list contract. The CLI
test seams `pickAddTUI`/`pickRemoveTUI` become one `pickServicesTUI`.

## 5. Deploy-time render (implements the stubbed render phase)

`Pipeline.render()` (internal/deploy/deploy.go) is implemented:

1. Compute `cfg.ServicesForEnv(env)`.
2. `stack.ForName(...).GenerateProdFiles(cfg, env)`.
3. **`docker-compose.prod.yml`**: merge into the existing local file
   via a new `MergeProd` (mirrors `MergeDev` in the laravel stack,
   reusing `mergeWithOwnership`/`mergeServicesMap` with a
   parameterized source-file name):
   - Owned services: `app`, `webserver`, and the effective sidecars.
     Fresh values win per key (via `compose.MergeNodes`).
   - User-added services in the existing file: preserved.
   - User-added keys on owned services (e.g. hand-written `AWS_*`
     `${...}` environment on `app` for AWS S3): preserved.
   - Pier services no longer in the effective list: **dropped** from
     the file (this is what makes remote teardown work).
   - Non-owned top-level keys: preserved via the existing
     keep/drop `Decision` mechanism (non-interactive: keep).
   - Written to the project root before the sync phase, so sync
     ships the fresh file. Deploys now mutate the local
     `docker-compose.prod.yml` to match pier.toml (git-visible,
     committable).
4. **`.env.production`**: **never clobbered, never pruned** — merge
   adds only keys the fresh render contains that are missing from the
   existing file (placeholder values like `DB_PASSWORD=changeme` when
   postgres is new to prod). Existing key values (real secrets) are
   preserved verbatim; stale keys (e.g. `DB_HOST=mysql` after a
   mysql→postgres switch, or `AWS_ENDPOINT` after s3 removal) are
   left alone — the compose app service sets DB_* directly and
   interpolates only `${APP_KEY}`/`${DB_PASSWORD}` from the env file,
   so stale copies are harmless for deployment. New helper
   `MergeEnvFile(existing string, fresh []byte) []byte` in the
   laravel stack.
5. `render()` return value simplifies from `(any, error)` to `error`.

Side-effect fix: `[deploy.<env>].ports` overrides finally take
effect — today the deployed compose is always init's render with
env `"production"`, which never matches the deploy env name, so
per-env ports were dead code.

## 6. Remote teardown

`Up` (internal/deploy/up.go) appends `--remove-orphans`:

```
docker compose --env-file .env.production -f docker-compose.prod.yml up -d --wait --wait-timeout 120 --remove-orphans
```

- Compose v2 removes containers carrying the project label that are
  not defined in the file — exactly the pier services dropped by the
  render merge. They are stopped and removed.
- Named volumes (`s3_data`, `mysql_data`, ...) are **not** removed —
  data survives a remove→re-add cycle.
- Containers from other compose projects or manual `docker run` are
  untouched.
- The rollback path calls the same `Up` — consistent.

## 7. Files touched

- `internal/config/config.go` — `DeployConfig.Services`,
  `Config.ServicesForEnv`.
- `internal/config/parse.go` — relaxed host/user/path/branch rule.
- `internal/stack/laravel/prod.go` — effective list in
  `GenerateProdFiles`/`renderProdCompose`.
- `internal/stack/laravel/merge.go` (or new `merge_prod.go`) —
  `MergeProd`, `MergeEnvFile`, parameterize source-file name in the
  shared merge helpers.
- `internal/tui/service.go` — `PickServices` replacing
  PickServicesToAdd/Remove.
- `internal/cli/service.go` — unified `pier service [env]`.
- `internal/cli/init.go` — `[deploy.production]` scaffold.
- `internal/deploy/deploy.go` — implement `render()`.
- `internal/deploy/up.go` — `--remove-orphans`.
- Tests for all of the above; README (CLI table, pier.toml docs,
  deploy docs) and CHANGELOG entry.

## 8. Testing

- config: scaffold relaxation (all-empty allowed, partial still
  rejected), `ServicesForEnv` (override vs inherit).
- laravel: effective-list render (`deploy.services` wins, DevOnly
  filtered), `MergeProd` (user service preserved, removed pier
  service dropped, user env keys on `app` preserved), `MergeEnvFile`
  (existing values kept, missing keys added, nothing deleted).
- cli: `pier service` dev flow (write + rerender + up added),
  `pier service <env>` (create table, no-op when unchanged, `[]`
  when all unticked), unknown env error, non-TTY error, init
  scaffold (pier.toml contains `[deploy.production]` with same
  services, validation passes).
- deploy: render phase writes merged compose + merged env file,
  up command includes `--remove-orphans`.

## 9. Out of scope

- Interactive per-service prompts at deploy time.
- Removing containers immediately from the `pier service` command
  (teardown happens on the next deploy).
- Pruning stale keys from `.env.production`.
- Non-interactive (`pier service <env> <name...>`) editing — manual
  pier.toml edits cover scripting.
